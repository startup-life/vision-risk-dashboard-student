# 4회차: 관련 기준 확인 (NotebookLM)과 작업 대기·알림

시작: `milestone-3` 브랜치(또는 지난 회차까지 내가 만든 코드)
끝나면: 사건 상세가 1 사진, 2 관련 기준 확인, 3 내 판단 남기기의 세 단계가 된다. "관련 기준 찾기"를 누르면 요청이 작업 대기열에 들어가고, 알림 패널에서 진행 상황과 경과 시간을 보며, 끝나면 NotebookLM 인용이 상세에 나온다. 예시 결과(mock)와 실제 NotebookLM(live) 둘 다 동작한다.

## 시작하기 전에

```powershell
git switch milestone-3
npm.cmd install
if (-not (Test-Path config/local-connection.json)) { Copy-Item config/local-connection.example.json config/local-connection.json }
npm.cmd start
```

- 내 코드로 이어 가면 `git switch`는 하지 않는다.
- 브라우저에서 `http://127.0.0.1:8765`를 열어 3회차 기능(사건 상세·정보 수정·판단·조치)이 되는지 본다.
- 지급 자료 `materials/factory-criteria-v1.txt`(NotebookLM에 올릴 기준 원문)가 있는지 본다.
- 앞부분(4-1 ~ 4-30)은 예시 결과(mock)로 화면 흐름을 끝낸다. 뒷부분(4-31 ~)에서 실제 NotebookLM에 연결한다.
- 서버 코드를 고친 단계 뒤에는 서버를 `Ctrl+C`로 끄고 `npm.cmd start`로 다시 켠다. 화면 코드만 고쳤으면 브라우저를 새로 고친다.

## 4-1. NotebookLM 연동 스위치
설정 파일에 NotebookLM을 켜고 끄는 스위치를 만든다.
```text
설정 파일 config/local-connection.json에 NotebookLM 연동 스위치 NOTEBOOKLM_MODE를 더해 줘. 값은 off, mock, live이고 비워 두면 live야.
허용하지 않는 값이면 서버가 켜지지 않고, 허용 값과 고칠 곳을 알려 주는 한 줄을 터미널에 보여 줘. 설정 값 자체는 출력하지 마.
NOTEBOOKLM_NOTEBOOK_ID, NOTEBOOKLM_SOURCE_IDS, NOTEBOOKLM_MCP_COMMAND도 설정 파일이 읽는 키 목록에 넣어 줘.
config/local-connection.example.json에는 지금 있는 키와 이 네 키를 모두 빈 값("")으로 적어 줘.
```
확인: 예시 파일에 키 다섯 개(`REPOSITORY_IMAGES_ROOT` 포함)가 빈 값으로 들어 있다.

## 4-2. 연동 상태 줄
지금 어떤 조합으로 켜졌는지 한 줄로 보이게 한다.
```text
서버를 켤 때 터미널에 '연동 상태: 저장소 로컬 저장 · NotebookLM mock'처럼 지금 쓰는 조합을 한 줄로 보여 줘. off는 '꺼짐'으로 적어 줘.
같은 줄을 /api/health의 integration_status에, 스위치 값을 modes.notebooklm에 넣어 줘.
화면 위 연동 상태 줄에도 '저장소 로컬 저장'과 'NotebookLM mock'을 두 칸으로 보여 줘.
```
확인: 아래 4-3을 한 뒤에 본다.

## 4-3. 스위치를 mock으로 두기 (직접 하기)
- `config/local-connection.json`을 메모장으로 열어 `"NOTEBOOKLM_MODE": "mock"`을 넣는다. 없는 키는 예시 파일을 보고 같은 모양으로 더한다(줄 끝 쉼표에 주의).
- 서버를 다시 켠다. 값을 잠깐 `abc`로 바꿔 켜 보고, 확인한 뒤 `mock`으로 되돌려 다시 켠다.

확인: 터미널과 화면 위에 `연동 상태: 저장소 로컬 저장 · NotebookLM mock`이 보인다. `abc`일 때는 서버가 켜지지 않고 허용 값(off, mock, live) 안내가 나온다.

## 4-4. 사건 상세를 세 단계로
상세의 확인 순서에 "관련 기준 확인" 단계를 넣는다.
```text
사건 상세의 확인 순서를 '1. 사진', '2. 관련 기준 확인 (NotebookLM)', '3. 내 판단 남기기' 세 단계로 바꿔 줘. 지금의 판단 영역은 3번이 돼.
상세를 열 때 진행 표시는 기준 확인 결과가 없으면 2단계, 있으면 3단계에 둬. 판단을 이미 저장한 사건은 지금처럼 완료·조치 상태를 따라.
안내 문구는 2단계 'NotebookLM으로 관련 기준을 찾아 사진과 비교해 주세요.', 3단계 '사진과 기준을 비교하고, 직접 확인한 판단을 남겨주세요.'로 해 줘.
2번 영역 끝에 '다음: 내 판단 남기기' 단추를 두고, 누르면 진행 표시와 안내가 3단계로 바뀌고 3번 영역으로 이동해 줘.
```
확인: 판단을 남기지 않은 사건을 열면 세 단계가 보이고 2단계가 현재 단계다. "다음: 내 판단 남기기"를 누르면 3단계로 바뀐다.

## 4-5. 확인할 기준 고르기
2번 영역에 기준 고르는 칸과 요청 단추를 둔다.
```text
2번 영역에 '무엇을 확인할까요?' 고르는 칸을 만들어 줘. standards.json의 기준 가운데 이 사건 분류와 같은 기준만 넣고, 처음에는 첫 기준을 골라 둬.
고른 기준 아래에 '확인할 점:'으로 그 기준의 위험 조건을 보여 주고, 접는 칸 '미리 읽어볼 기준'에 기준 원문과 보류 조건을 넣어 줘.
그 아래에 '관련 기준 찾기' 단추와 '사건 정보(분류·장소·메모·사진 장수)로 질문합니다.' 안내를 둬. 단추는 아직 아무 일도 하지 않아도 돼.
```
확인: 산업안전 사건에는 산업안전 기준만, 택배 발송 확인 사건에는 택배 기준만 고르는 칸에 나온다. 기준을 바꾸면 "확인할 점"이 바뀐다.

## 4-6. 연동이 꺼졌을 때
NotebookLM을 끄면 단추가 꺼지고 2단계를 건너뛴다.
```text
NOTEBOOKLM_MODE가 off이면 '관련 기준 찾기' 단추를 끄고 그 아래에 'NotebookLM 연동이 꺼져 있습니다(NOTEBOOKLM_MODE=off).'를 보여 줘.
화면은 /api/health의 modes로 스위치를 알아내고, 아직 모르면 단추를 켜 둬.
off일 때 상세의 진행 표시는 2단계를 건너뛰고 3단계에서 시작해 줘.
```
확인: 설정을 `off`로 바꿔 서버를 다시 켜면 단추가 꺼지고 안내가 보이며, 화면 위에 `NotebookLM 꺼짐`이 보인다. 확인한 뒤 `mock`으로 되돌린다.

## 4-7. 질문 만들기와 예시 결과
NotebookLM에 보낼 질문과, 연결 전에 쓸 예시 결과를 서버에 만든다.
```text
서버에 기준 확인용 질문을 만드는 기능을 만들어 줘. 저장된 사건 정보로 '분류: 산업안전 | 장소: … | 현장 메모: … | 현장 사진 3장'처럼 만들고, 메모 끝에 붙은 저장소 사진 출처 부분은 빼 줘.
NOTEBOOKLM_MODE가 mock이면 NotebookLM 대신 예시 결과를 돌려줘. 고른 기준의 standards.json 원문을 인용문으로 쓰고, 소스 ID는 'src-standards-v1', 노트북 ID는 'mock-notebook'으로 채워 근거 충분으로 판정해.
답변은 '[1] 기준 원문 대조 결과: <인용문>'으로 해 줘. 질문에 '가림', '불명확', '반사'가 들어 있으면 같은 인용을 주되 근거 부족(판단 보류 조건)으로 판정해 줘.
```
확인: 아직 화면 변화는 없다. 서버가 오류 없이 다시 켜진다.

## 4-8. 작업 대기열 API
요청을 바로 처리하지 않고 작업으로 만들어 순서대로 처리한다.
```text
'관련 기준 찾기' 요청을 받는 API POST /api/records/:id/evidence-check를 만들어 줘. 바로 처리하지 말고 작업을 만들어 대기열에 넣은 뒤 202로 작업 번호를 돌려줘.
작업은 대기, 진행, 완료, 실패, 중단 상태를 가지고, 서버는 한 번에 한 작업만 순서대로 처리해. 작업마다 사건 번호, 요청 번호, 고른 기준, 질문, 사건 버전, 요청 시각을 남겨 줘.
GET /api/jobs(사건·상태로 거르기)와 GET /api/jobs/:id로 작업을 조회하게 해 줘. NOTEBOOKLM_MODE가 off면 요청을 409와 INTEGRATION_OFF로 거절해.
```
확인: 브라우저에서 `http://127.0.0.1:8765/api/jobs`를 열면 빈 작업 목록이 보인다.

## 4-9. 작업을 파일로 남기기
서버를 껐다 켜도 작업 기록이 남게 한다.
```text
작업은 사건 기록 파일과 같은 폴더의 _synthetic_jobs 폴더에 한 건씩 JSON 파일로 저장해 줘. 상태가 바뀔 때마다 임시 파일에 쓴 뒤 이름을 바꿔 덮어써.
이 폴더는 .gitignore에 넣고, 브라우저 주소로 열리지 않게 막아 줘. 작업 파일에 키나 토큰처럼 보이는 값은 가려서 저장해 줘.
```
확인: `git status`에 작업 폴더가 나오지 않는다(작업이 생긴 뒤에 다시 본다).

## 4-10. 같은 요청 두 번 막기
같은 요청이 두 번 와도 작업이 하나만 생기게 한다.
```text
같은 요청 번호로 같은 내용이 다시 오면 새 작업을 만들지 말고 처음 작업을 돌려줘. 같은 요청 번호인데 내용(사건 버전·기준·질문)이 다르면 409로 거절해.
한 사건에 대기·진행 중인 작업이 있는데 다른 내용으로 또 요청하면 409로 거절하고, 같은 내용이면 그 작업을 돌려줘.
```
확인: 서버가 오류 없이 다시 켜진다. 화면에서는 기다리는 동안 단추가 꺼져 같은 요청을 두 번 보낼 수 없어서, 이 규칙은 화면으로 따로 확인하지 않는다.

## 4-11. 결과를 사건 기록에 저장
끝난 작업의 결과를 사건 기록에 남기고 상세 API로 돌려준다.
```text
작업이 끝나면 결과를 먼저 작업 파일에 남기고, 그 다음 사건 기록의 기준 확인 목록에 저장해 줘. 저장 값은 요청 번호, 기준, 노트북·소스 ID, 답변, 인용문, 일치 여부, 근거 충분 여부, 메모, 사건 버전, 저장 시각이야.
저장소 저장이 실패하면 작업은 실패로 끝내 줘. 감사 이력에는 단계 'NotebookLM 대조', 작업 '기준 근거 대조', 작업자 'NotebookLM MCP'로 한 줄 남겨 줘(mock이면 '(mock)'을 붙여).
사건 상세 API는 최신 기준 확인 결과와, 기준마다 가장 최근 결과(이 서버가 끝낸 작업과 저장된 최신 결과)를 함께 돌려줘.
```
확인: 서버가 오류 없이 다시 켜진다.

## 4-12. 단추로 요청 보내기
"관련 기준 찾기"를 누르면 요청을 보내고 상태를 보여 준다.
```text
'관련 기준 찾기'를 누르면 고른 기준과 새 요청 번호로 기준 확인을 요청해 줘. 요청 번호는 보내기 전에 화면에서 만들어.
2번 영역 위에 요청 상태를 한 줄로 보여 줘. 보내는 중 '요청을 보내고 있어요.', 대기 '서버 대기열에 등록되었습니다. 순서대로 처리됩니다.', 진행 '분석이 진행 중입니다. 잠시만 기다려 주세요...', 완료 '완료되었습니다.'.
기다리는 동안 단추는 꺼지고 '기준 근거 대조 중...'으로 바뀌어. 화면은 2초마다 작업 상태를 확인하고, 끝나면 단추를 다시 켜 줘.
```
확인: 단추를 누르면 상태 줄이 바뀌고 곧 "완료되었습니다."가 보인다. 예시 결과는 바로 끝나서 대기·진행 상태는 잠깐만 보인다.

## 4-13. 결과 보여 주기
끝난 결과를 2번 영역에 보여 준다.
```text
작업이 끝나면 화면 전체를 다시 그리지 말고 상세의 2·3번 영역과 진행 표시만 새 결과로 바꿔 줘. 다른 화면에 있으면 그 화면은 건드리지 마.
결과에는 판정 제목, 답변 앞부분(240자), '인용한 기준: … · 소스 ID: …' 한 줄, 인용 상자, 접는 칸 '전체 답변'을 보여 줘.
근거 충분이 아니면 제목을 '근거를 충분히 찾지 못했습니다', 충분하면 '문서에서 관련 근거를 찾았습니다'로 해 줘.
```
확인: 결과 제목 "문서에서 관련 근거를 찾았습니다", 소스 ID `src-standards-v1`, 인용 상자에 기준 원문이 보인다.

## 4-14. 인용이 어느 기준의 문장인지 대조
NotebookLM 인용이 고른 기준의 문장인지 화면에서 한 번 더 본다.
```text
인용문이 어느 기준의 문장인지 standards.json의 기준(이름·원문·참고)과 공백 차이를 무시하고 비교해 '인용한 기준'에 적어 줘. 여러 개면 모두 적고, 없으면 '등록된 기준 문장에서 찾지 못했습니다', 인용이 비었으면 '인용문 없음'이야.
제목은 근거 충분 결과일 때만 이 대조로 정해(근거 부족 결과는 '근거를 충분히 찾지 못했습니다' 그대로). 인용 안에 고른 기준의 원문이 통째로 있거나 인용이 고른 기준 한 곳에만 있으면 '문서에서 관련 근거를 찾았습니다'로 둬.
다른 기준의 문장이면 '선택한 기준과 다른 기준의 문장입니다', 여러 기준에 함께 있으면 '어느 기준의 문장인지 정할 수 없습니다', 어디에도 없으면 '등록된 기준 문장과 일치하지 않습니다'로 바꿔 줘.
바꾼 경우에는 제목 아래 '확인 필요:'로 이유를 한 줄 적어 줘. 저장된 판정 값은 바꾸지 마.
```
확인: "인용한 기준: C-01 머리 보호구"처럼 고른 기준이 보인다.

## 4-15. 전체 답변 읽기 좋게
NotebookLM 답변의 마크다운을 간단히 보여 준다.
```text
'전체 답변' 칸에서는 답변의 '#' 제목 줄을 굵게, '* '·'- ' 목록 줄을 '• '로, '**굵게**'를 굵게 보여 줘. 답변 앞부분 240자에도 같은 규칙을 써.
'> ' 다음에 따옴표나 글자가 오는 줄만 인용 모양으로 보여 주고('> 5bar' 같은 비교는 그대로 둬), 나머지 글자는 HTML로 해석하지 말고 글자 그대로 보여 줘.
```
확인: "전체 답변"을 펼치면 답변이 보인다(실제 모양은 4-41 live에서 본다).

## 4-16. 기준을 바꿔 보기
고른 기준의 결과만 보이게 한다.
```text
고르는 칸에서 기준을 바꾸면 그 기준으로 확인한 결과만 보여 줘. 그 기준으로 확인한 적이 없으면 '이 기준으로는 아직 확인하지 않았습니다.' 뒤에 ' 가장 최근 확인은 C-01 머리 보호구 기준입니다.'처럼 최근 기준을 알려 줘.
요청 상태 줄도 지금 고른 기준과 사건 버전의 끝난 작업만 보여 줘. 진행 중인 작업은 기준과 상관없이 보여 줘.
```
확인: 다른 기준을 고르면 "아직 확인하지 않았습니다"가, 처음 기준으로 돌아오면 그 결과가 다시 보인다.

## 4-17. 예시 결과 흐름 확인 (직접 하기)

- 메모에 "반사"가 들어간 사건을 새로 등록해 같은 기준으로 확인한다.

확인: 두 번째 사건은 "근거를 충분히 찾지 못했습니다"가 보인다. 상세를 새로 고치면 아래 감사 이력에 "NotebookLM 대조" 줄이 늘어 있다.

## 4-18. 요청 알림 벨과 패널
머리말에 요청 알림을 모아 보는 패널을 만든다.
```text
머리말에 요청 알림 벨 단추를 두고 닫지 않은 알림 수를 숫자로 보여 줘. 누르면 '요청 알림' 패널이 열리고, '닫기' 단추·Esc 키·패널 바깥 클릭으로 닫혀.
알림 목록은 페이지를 열 때 GET /api/jobs로 받은 기준 확인 작업(닫은 것은 빼고)과 지금 보내는 요청으로 만들고, 하나씩 제목, '사건 R-101', 설명으로 보여 줘. 알림이 없으면 '새로운 요청 알림이 없습니다.'를 보여 줘.
제목은 보내는 중 '기준 근거 대조 요청 전송 중...', 대기 '기준 근거 대조 접수', 진행 '기준 근거 대조 중', 완료 '기준 근거 대조가 완료됐습니다.', 실패 '기준 근거 대조 실패', 중단 '처리가 중단됐습니다'로 해 줘.
진행 중 설명에는 '다른 사건을 확인해도 됩니다. 준비되면 사이트에서 알려드릴게요.'를 넣어 줘.
```
확인: 페이지를 새로 고쳐도 4-17에서 요청한 건이 패널에 "기준 근거 대조가 완료됐습니다."로 보이고 벨 숫자가 맞다.

## 4-19. 결과 보기와 닫기
알림에서 결과로 가고, 다 본 알림을 닫는다.
```text
완료된 알림에는 '결과 보기' 단추를 두고, 누르면 그 사건 상세를 열고 그 작업의 기준을 골라 결과를 보여 줘. 상세를 연 뒤에 그 알림을 확인 처리해.
끝난 알림(완료·실패·중단)에는 '닫기' 단추를 두고, 누르면 POST /api/jobs/:id/ack로 서버에 확인 표시를 남기고 패널과 숫자에서 빼 줘.
알림 패널과 숫자는 어느 화면에서나 갱신되게 하고, 이때 화면 전체를 다시 그리지 마.
```
확인: 홈에서 "결과 보기"를 누르면 그 사건 상세로 가서 결과가 보이고, 벨 숫자가 줄어든다. "닫기"로 닫은 알림은 새로 고쳐도 다시 나오지 않는다.

## 4-20. 경과 시간
기다리는 동안 얼마나 지났는지 보여 준다.
```text
대기·진행 중인 요청 옆에 '12초 지남', '1분 5초 지남'처럼 요청한 뒤 지난 시간을 보여 줘. 2번 영역 상태 줄과 알림 패널 둘 다야.
시간은 단추를 누른 시각부터 세고, 1초마다 그 글자만 바꿔 줘(화면 전체를 다시 그리지 않음).
```
확인: 예시 결과는 금방 끝나 "0초 지남", "1초 지남"이 잠깐 보이거나 보이지 않는다. 초가 계속 올라가는지는 4-41 live에서 본다.

## 4-21. 새로 고침 뒤 요청 이어 보기
기다리는 중에 새로 고쳐도 요청을 잃지 않게 한다.
```text
기다리는 중에 새로 고쳐도 요청이 이어 보이게 해 줘. 화면은 진행 중인 요청을 sessionStorage에 남기고(키·토큰은 넣지 않음), 페이지를 열 때 받는 서버 작업 목록에서 대기·진행 중인 것은 2초마다 상태 확인을 다시 시작해.
상세를 새로 고쳤으면 기다리던 요청의 기준을 다시 골라 두고 단추도 꺼진 채로 보여 줘. 그래서 상세는 작업 목록을 받은 뒤에 그려 줘.
```
확인: 4-41 live에서 기다리는 중에 새로 고쳐 본다(live를 못 하면 이 확인은 건너뛴다).

## 4-22. 보내는 중에 끊긴 요청
응답을 받지 못한 요청이 두 번 실행되지 않게 한다.
```text
보내는 중에 새로 고쳤거나 연결이 끊겨 응답을 못 받았으면, 서버 작업 목록에서 같은 요청 번호를 찾아 있으면 그 작업을 이어 봐. 자동으로 다시 보내지는 마.
목록에 없으면 '요청이 서버에 닿지 않았습니다. 다시 요청해 주세요.'를 보여 주고 단추를 켜 줘. 같은 기준으로 다시 누르면 같은 요청 번호로 보내.
목록도 받지 못했으면 '전송 상태 확인 필요'로 두고, 확인될 때까지 그 사건의 새 요청을 막아 줘.
```
확인: 서버를 끈 채로 열려 있던 상세에서 단추를 누르면 "전송 상태 확인 필요"가 보이고 단추가 꺼진다. 서버를 다시 켜고 새로 고치면 "요청이 서버에 닿지 않았습니다. 다시 요청해 주세요."로 바뀌고 단추가 켜진다.

## 4-23. 서버를 다시 켤 때 작업 정리
서버가 꺼질 때 남은 작업을 다음에 켤 때 정리한다.
```text
서버를 켤 때 작업 폴더의 작업 파일을 읽어 정리해 줘. 진행 중이던 작업은 저장소에 같은 요청 번호의 결과가 있으면 완료로, 없으면 중단으로 바꿔. 대기 중이던 작업도 중단으로 바꿔.
중단된 작업은 자동으로 다시 실행하지 마. 상태 줄과 알림에는 '처리가 중단됐습니다. 저장된 결과를 확인해 주세요.'를 보여 줘.
작업 파일이 깨져 읽을 수 없으면 지우지 말고 그대로 두고, 기준 확인 요청을 503 SERVICE_UNAVAILABLE로 거절해.
```
확인: 서버를 다시 켜도 4-17의 완료 작업이 `/api/jobs`에 그대로 있다. 중단 표시는 4-42 live에서 본다(live를 못 하면 이 확인은 건너뛴다).

## 4-24. 작업 폴더는 서버 하나만
서버 두 개가 같은 작업 폴더를 쓰지 못하게 한다.
```text
작업 폴더에 잠금 파일(서버 프로세스 번호와 갱신 시각)을 두어 서버 두 개가 같은 작업 폴더를 쓰지 못하게 해 줘. 켜진 서버는 30초마다 갱신 시각을 바꿔.
새 서버는 잠금을 가진 서버 프로세스가 이미 없거나 잠금이 2분 넘게 갱신되지 않았으면 바로 넘겨받아.
잠금을 얻지 못하면 서버 콘솔에 이유를 남기고 기준 확인 요청을 503 SERVICE_UNAVAILABLE로 거절해. 잠금 파일도 브라우저 주소로 열리지 않게 해 줘.
포트를 먼저 잡은 뒤에 잠금과 작업 정리를 하고, 그동안 들어온 요청은 정리가 끝날 때까지 기다리게 해 줘.
```
확인: 서버를 `Ctrl+C`로 끄고 바로 다시 켜도 "관련 기준 찾기"가 동작한다(끈 서버의 프로세스가 없으니 잠금을 바로 넘겨받는다).

## 4-25. 서버 끄기
끌 때 작업 잠금이 남지 않게 한다.
```text
Ctrl+C로 끌 때 실행 중인 작업을 5초까지 기다리고, 그래도 안 끝나면 '실행 중인 작업이 5초 안에 끝나지 않아 작업 잠금을 풀고 종료한다.'를 보여 주고 잠금을 푼 뒤 꺼 줘.
Ctrl+C를 한 번 더 누르면 기다리지 않고 바로 꺼. 터미널 창을 닫거나 Ctrl+Break로 끌 때도 잠금을 풀어 줘.
```
확인: `Ctrl+C`로 끈 뒤 작업 폴더에 잠금 파일이 남지 않는다. 5초 안내와 두 번째 `Ctrl+C`는 예시 결과가 금방 끝나 4-42 live에서 본다(live를 못 하면 건너뛴다).

## 4-26. 홈 카드에 출처 대조 표시
홈 사건 카드에서 기준 확인 상태를 바로 보이게 한다.
```text
사건 목록·상세 API의 요약에 최신 기준 확인 결과를 넣고, 그 결과 뒤에 사건 정보가 수정됐는지도 알려 줘.
홈 사건 카드에 '출처 대조:' 한 줄을 더해 줘. 결과가 없으면 '근거 미확인', 찾았으면 '출처 대조 완료', 인용 기준이 맞지 않으면 '인용 기준 확인 필요', 근거 부족이면 '근거 부족'이야.
결과 뒤에 정보를 수정했으면 '수정 전 기준 대조됨 (재확인 권장)'으로 보여 줘. 기준 확인 결과가 있는 사건의 카드 단추는 '이어서 확인'으로 해 줘.
```
확인: 4-17의 두 사건 카드에 "출처 대조 완료"와 "근거 부족"이 보이고 단추가 "이어서 확인"이다.

## 4-27. 수정 전 결과 표시
사건 정보를 고친 뒤 예전 결과임을 알린다.
```text
사건 정보를 고친 뒤 보이는 예전 기준 확인 결과 위에 '수정 전 결과입니다. 현재 사진과 내용을 다시 확인해 주세요.'를 붙여 줘.
상세 위의 정보 변경 안내도 기준 확인 뒤에 수정한 경우를 포함해 줘. 이때 진행 표시는 다시 2단계에서 시작해.
```
확인: 결과가 있는 사건의 장소를 고치면 홈 카드는 "수정 전 기준 대조됨 (재확인 권장)", 상세는 "수정 전 결과입니다"가 보인다. 다시 "관련 기준 찾기"를 누르면 사라진다.

## 4-28. 판단 화면에 기준 확인 결과
판단을 남길 때 기준 확인 결과를 함께 본다.
```text
'내 판단 남기기' 화면의 판정 칸 위에 'NotebookLM 기준 확인:' 칸을 두고, 상세에서 고른 기준의 결과 제목, 확인 필요, 답변 앞부분, 인용, 인용한 기준, 소스 ID를 보여 줘.
결과가 없으면 'C-01 머리 보호구 기준으로는 아직 확인하지 않았습니다.'처럼 보여 주고, 고른 기준이 없으면 '아직 관련 기준을 확인하지 않았습니다.'로 해 줘. 수정 전 결과면 '(수정 전 결과)'를 붙여 줘.
```
확인: 4-17의 사건에서 "판단 기록하기"로 들어가면 위에 NotebookLM 기준 확인 결과가 보인다.

## 4-30. 예시 결과 단계 마무리 (직접 하기)

- `git status`로 `config/local-connection.json`과 작업 폴더가 목록에 없는지 본다.

확인: 예시 결과로 요청, 알림, 결과 보기, 닫기, 기준 바꾸기가 모두 된다.

## 4-31. uv와 nlm 설치 (직접 하기)
실제 NotebookLM을 쓰는 도구를 설치한다. Antigravity 아래 터미널(PowerShell)에서 친다.
```powershell
powershell -ExecutionPolicy ByPass -c "irm https://astral.sh/uv/install.ps1 | iex"
```
- 설치가 끝나면 터미널 창을 닫고 새로 연 뒤 아래를 친다.
```powershell
uv tool install notebooklm-mcp-cli==0.15.6
nlm --version
```
- `nlm`을 찾을 수 없다고 나오면 `uv tool update-shell`을 치고 Antigravity를 완전히 닫았다 다시 연다. 그래도 없으면 `%USERPROFILE%\.local\bin`이 PATH에 있는지 본다.

- 모두 같은 판을 쓰도록 판 번호(0.15.6)를 붙여 설치한다. 나중에 `Update available`이나 `uv tool upgrade` 안내가 나와도 올리지 않는다.

확인: `nlm --version`이 0.15.6이 들어 있는 버전 줄을 보여 준다. 함께 설치된 `notebooklm-mcp`는 서버가 PATH에서 찾는다.

## 4-32. NotebookLM 로그인 (직접 하기)
로그인은 5분 안에 끝내야 하므로 에이전트에게 시키지 않고 직접 친다.
```powershell
nlm login --storage protected
```
- nlm 전용 Chrome 창이 새로 뜬다. 첫 화면(Gemini Notebook 소개)에서 `Sign in`을 눌러 NotebookLM을 쓸 본인 계정으로 로그인한다. 성공 줄이 나올 때까지 터미널과 창을 닫지 않는다.
- 로그인 상태를 확인한다. 화면에 나오는 계정 메일은 대화창에 옮기지 않는다.
```powershell
nlm login --check
```
확인: `✓ Authentication valid!`가 나온다.

막히면: 키 저장소 오류가 나오고 `--storage file`을 쓰라는 안내가 보이면 `nlm login --storage file`로 다시 한다.

## 4-33. 노트북 만들고 기준 원문 올리기 (직접 하기)
프로젝트 폴더의 터미널에서 친다. `<노트북 ID>`는 꺾쇠까지 지우고 실제 ID로 바꾼다.
```powershell
nlm notebook create "현장 리스크 기준" --json
nlm source add <노트북 ID> --file materials/factory-criteria-v1.txt --wait
nlm source list <노트북 ID>
```
- 첫 명령이 출력한 `"notebook_id"`가 노트북 ID, 마지막 명령에 나온 ID가 소스 ID다.
- `config/local-connection.json`의 `NOTEBOOKLM_NOTEBOOK_ID`와 `NOTEBOOKLM_SOURCE_IDS`에 직접 넣는다(소스가 여러 개면 `"ID1,ID2"`처럼 쉼표로). 이 값은 대화창·메신저·커밋에 붙여 넣지 않는다.
- `NOTEBOOKLM_MODE`는 아직 `mock`으로 둔다.

확인: 둘째 명령 끝에 `(ready)`가 붙은 줄이 나오고, notebooklm.google.com에서 "현장 리스크 기준" 노트북에 소스가 1개 있다.

## 4-34. MCP 라이브러리와 연결
서버가 내 PC의 NotebookLM MCP 프로그램을 직접 실행해 연결하게 한다.
```text
@modelcontextprotocol/sdk 라이브러리를 설치하고(npm.cmd install @modelcontextprotocol/sdk), 서버가 내 PC의 NotebookLM MCP 프로그램을 실행해 stdio로 연결하게 해 줘.
연결은 처음 필요할 때 한 번만 하고, 동시에 온 요청이 프로그램을 두 번 띄우지 않게 해. 프로그램이 끝나면 다음 요청 때 새로 연결해.
서버를 끌 때는 MCP 연결도 닫아 줘. 아직 질의는 바꾸지 마.
```
확인: `package.json`의 dependencies에 `@modelcontextprotocol/sdk`가 들어 있고 서버가 다시 켜진다.

## 4-35. MCP 실행 파일 찾기
어디에 설치했든 실행 파일을 찾게 한다.
```text
MCP 실행 파일은 이 순서로 찾아 줘. 1) 설정 NOTEBOOKLM_MCP_COMMAND(실행 때 --transport stdio를 붙임) 2) %USERPROFILE%\.gemini\config\mcp_config.json, 없으면 %USERPROFILE%\.gemini\antigravity\mcp_config.json의 mcpServers 아래 gemini-notebook-mcp 항목(command·args·env 그대로) 3) PATH의 notebooklm-mcp(--transport stdio를 붙임).
설정 파일이 비었거나 JSON 오류면 다음 순서로 넘어가. Windows에서는 PATHEXT 확장자(.exe 등)를 붙여 찾고, 못 찾았으면 실행하지 마.
NOTEBOOKLM_MODE가 live인데 실행 파일을 못 찾으면 터미널 연동 상태 줄을 'NotebookLM live(실행 파일을 찾지 못함: notebooklm-mcp를 설치하거나 NOTEBOOKLM_MCP_COMMAND를 지정)'로 보여 줘.
```
확인: mock에서는 상태 줄이 그대로다(live 확인은 4-41).

## 4-36. MCP에 넘길 환경 변수
MCP 프로그램에는 필요한 값만 넘긴다.
```text
MCP 프로그램에는 라이브러리 기본 변수(PATH 등), NOTEBOOKLM_로 시작하는 변수, TMP·TMPDIR·LANG·LC_ALL·LC_CTYPE, 프록시(HTTP_PROXY·HTTPS_PROXY·NO_PROXY·ALL_PROXY), 인증서 위치(SSL_CERT_FILE·SSL_CERT_DIR·REQUESTS_CA_BUNDLE), Antigravity 항목의 env만 넘겨 줘.
고정값 NOTEBOOKLM_HL=ko, NOTEBOOKLM_RATE_LIMIT_MAX_RETRIES=0, NOTEBOOKLM_DISABLE_HEADLESS_REFRESH=1을 함께 넘겨 줘. REPOSITORY_IMAGES_ROOT 같은 서버 설정값은 넘기지 마.
Windows에서는 변수 이름의 대소문자를 가리지 않게 해 줘.
```
확인: 서버가 다시 켜진다.

## 4-37. 연결 상태를 /api/health에
MCP 연결과 로그인 상태를 주소 하나로 확인하게 한다.
```text
/api/health에 mcp_status를 더해 줘. MCP에 연결되면 connected를 true로 하고, server_info 도구(인자 없음) 응답 JSON의 auth_status를 authStatus(configured, not_configured, stale 등)에 넣어 줘. 읽지 못하면 unknown이나 error로 둬.
연결하지 못하면 authStatus를 unreachable로 두고 error_code를 정해 줘. 어디에도 정하지 않았고 PATH에도 없으면 MCP_NOT_CONFIGURED, 설정·Antigravity 항목으로 정한 실행 파일이 없으면 MCP_EXECUTABLE_NOT_FOUND, 실행됐지만 응답 전에 끝나면 MCP_EXITED, 그 밖은 MCP_UNREACHABLE.
error에는 확인한 위치마다 무엇이 없었는지와 할 일(notebooklm-mcp 설치나 NOTEBOOKLM_MCP_COMMAND 지정)을 적어 줘.
NOTEBOOKLM_MODE가 off면 MCP를 실행하지 말고 authStatus를 off로 둬. server_info 결과에 든 메일 주소는 빼고 보내 줘.
```
확인: 4-31 ~ 4-33을 했으면 `http://127.0.0.1:8765/api/health`에서 `mcp_status.connected`가 `true`, `authStatus`가 `configured`이고 메일 주소는 보이지 않는다. 아직 준비 전이면 `authStatus`가 `unreachable`이고 `error_code`와 위치별 이유가 보인다.

## 4-38. 실제 NotebookLM에 질문하기
live에서는 예시 결과 대신 실제 노트북에 질문한다.
```text
NOTEBOOKLM_MODE가 live면 MCP의 notebook_query 도구에 인자 notebook_id(설정의 노트북 ID), source_ids(설정의 소스 ID 목록), query, timeout(120)을 넘겨 질문해 줘. 호출 전체는 135초까지 기다려.
query는 '현장 기준 C-01(머리 보호구) 관련: <사건 정보 질문> 답변 끝에 추가 질문이나 제안을 붙이지 마세요.'로 해.
응답 content의 글은 JSON이야. answer를 답변으로, references 첫 항목의 cited_text를 인용문, source_id를 인용 소스로 써 줘. status가 error면 근거 부족이 아니라 질의 실패로 처리해.
서버가 켜진 뒤 첫 질의 전에 한 번 server_info의 auth_status를 보고, configured가 아니면 질의하지 마.
```
확인: 4-41에서 live로 바꿔 본다.

## 4-39. 인용 검증
실제 인용이 내 노트북 원문에 그대로 있는지 확인한다.
```text
실제 결과는 이 순서로 확인해 줘. 인용 소스가 없거나, 인용문이 비었거나, 인용 소스가 설정의 소스 ID 목록에 없으면 근거 부족으로 판정해.
통과하면 source_get_content 도구에 인자 source_id(인용 소스)를 넘겨 원문을 받아. 원문은 응답 JSON의 content이고, status가 success가 아니거나 호출이 실패하면 작업을 실패로 끝내.
공백 차이만 무시하고 인용문이 원문에 그대로 있는지 봐. 있으면 근거 충분, 없거나 원문이 비었으면 근거 부족이고, 판정 이유는 결과 메모에 한 줄로 남겨 줘.
```
확인: 4-41에서 본다.

## 4-40. 실패했을 때 안내
실패하면 무엇을 고쳐야 하는지 화면에 보여 준다.
```text
실제 연결이 실패하면 작업을 실패로 끝내고 상태 줄과 알림에 이유를 보여 줘. 로그인이 안 됐거나 만료됐으면 'nlm login --storage protected로 로그인한 뒤 로컬 서버를 다시 시작하세요'를 넣어 줘.
노트북 ID나 소스 ID가 비었으면 채울 키(NOTEBOOKLM_NOTEBOOK_ID, NOTEBOOKLM_SOURCE_IDS)를 알려 주고, 질의 오류면 'NotebookLM 질의가 실패했습니다: <이유>'를 보여 줘.
시간이 넘으면 'NotebookLM 응답 시간이 지났습니다. 잠시 뒤 관련 기준 찾기를 다시 눌러 주세요.'를 보여 줘.
같은 요청 번호가 다른 내용으로 거절되면(409) '요청 사이에 사건 정보가 바뀌었습니다. 다시 요청해 주세요.'를 보여 줘.
```
확인: 4-41의 "막히면"에서 본다.

## 4-41. live로 바꿔 확인 (직접 하기)
- `config/local-connection.json`의 `NOTEBOOKLM_MODE`를 `live`로 바꾸고 서버를 다시 켠다.
- 터미널 상태 줄이 `연동 상태: 저장소 로컬 저장 · NotebookLM live`이고 "실행 파일을 찾지 못함"이 붙지 않았는지 본다. `/api/health`의 `authStatus`가 `configured`인지 본다.
- 새 사건을 하나 등록하고 상세에서 "관련 기준 찾기"를 누른다. 보통 40~60초 걸린다.
- 기다리는 동안 벨을 눌러 알림 패널을 보고, 상세 화면을 한 번 새로 고친다.

확인: 상태 줄과 알림 패널에 "N초 지남"이 1초마다 올라가고, 새로 고친 뒤에도 같은 요청이 이어 보이며 단추가 꺼져 있다. 끝나면 판정 제목, 인용, 내 소스 ID, "전체 답변"(한국어)이 보인다.

막히면: 상태 줄에 `nlm login` 안내가 보이면 4-32를 다시 하고 서버를 다시 켠다. 노트북·소스 ID 안내가 보이면 4-33의 값을 넣었는지 본다. 응답 시간 안내가 보이면 1분쯤 뒤 다시 누른다.

## 4-42. 서버 재시작 때 작업 정리 확인 (직접 하기)
- 다른 사건에서 "관련 기준 찾기"를 누르고, 끝나기 전에 서버를 `Ctrl+C`로 끈다. 5초 안내가 나오면 기다리거나 `Ctrl+C`를 한 번 더 누른다.
- 서버를 다시 켜고 그 사건 상세와 알림 패널을 본다.
